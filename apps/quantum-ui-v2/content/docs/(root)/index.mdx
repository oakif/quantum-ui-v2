**Quantum UI is not a fork you drop in. It's a design system you build up.**

The foundation comes from [shadcn/ui](https://ui.shadcn.com) and its ecosystem of components and forks. But instead of pulling in components unchanged, Quantum follows a selective porting workflow:

1. **Study** the interaction and layout of an upstream or forked component.
2. **Check the license** if you plan to reuse code verbatim.
3. **Adapt or rebuild** it inside Quantum using your own primitives, tokens, and conventions.
4. **Standardize** it before promoting it to the component catalog.

This means every component in Quantum has been reviewed, customized, and approved — not just copied.

## Why This Approach

Traditional forks drift. You pull in hundreds of components, customize a few, and then upstream updates become painful merges. Quantum avoids this by:

- **Keeping the upstream reference intact** (`apps/v4`) as a pristine copy of shadcn/ui.
- **Working in an isolated app** (`apps/quantum-ui-v2`) where all customizations live.
- **Porting selectively** — only the components you actually need, one at a time.

When upstream releases something useful, you can compare it against your version and decide whether to adopt, adapt, or ignore it.

## How Components Get Added

1. Identify a component you need (from shadcn/ui, a fork, or built from scratch).
2. Implement it in the Quantum registry with your design tokens and conventions.
3. Add a demo to the home page or a dedicated test surface.
4. Review it visually in the running app.
5. Once approved, commit it and it appears in the component catalog.

## AI-Ready

Quantum UI is designed for LLM-assisted development. The open code and consistent API make it straightforward for AI models to:

- Read and understand existing components.
- Generate new components that match the design system.
- Port components from upstream by studying the source and adapting it.

See the [Installation](/docs/installation) page for how to use Quantum UI with an LLM.
